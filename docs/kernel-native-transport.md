# 在内核里重建 Queqiao 的传输能力

**调研与实验记录**

---

## 这份文档是什么

Queqiao 是一个自托管的长链路加速传输协议。它的核心是一套**传输策略**：在丢包率很高的路径上，
既不放弃带宽，也不把丢包误当成拥塞而错误退让。

这份文档记录两件事：

1. **内核到底提供了什么** —— 用 eBPF 和内核自带机制，能把 Queqiao 的哪一部分搬进内核，
   搬不动的部分卡在哪里。
2. **实测数据** —— 在一个能精确注入丢包的实验台里，量出"多 IP 通道"和"FEC"分别值多少。

文档按"先讲清楚问题，再讲手段，最后讲结论"的顺序写。第一次出现的名词都会就地解释，
不熟悉内核网络栈的读者可以顺序读下来而不需要先备一堆缩写。

### 结论速览

| # | 结论 | 证据 |
| --- | --- | --- |
| 1 | Queqiao 的**控制策略可以完整搬进内核**，用内核的"BPF 拥塞控制"接口实现，零用户态参与 | 实测：内核调用该控制器 412 次，实时维护延迟与带宽估计 |
| 2 | 内核**不允许** eBPF 在包路径上做加密，内核自带的 AEAD 接口对普通程序关闭 | 实测：装载被内核拒绝 |
| 3 | **"丢包是运营商按 IP 算的"这个假设成立**，三个源地址 ≈ 2.85 倍交付容量 | 实测：单通道 11.45 Mbit/s，三通道 32.62 Mbit/s |
| 4 | FEC 传输在 40% 丢包路径上比 TCP 快 **500～1500 倍** | 实测：TCP 0.063 Mbit/s，FEC 97.4 Mbit/s |
| 5 | 但**传输层必须在 IP 之上**：TCP 钉死四元组，无法跨地址聚合 | 原理 + 实测（IP 层重复拷贝只能把丢包降到 16%，TCP 仍不可用） |

# 第一部分 · 问题

## 1. Queqiao 面对的是什么

### 1.1 一条很长的、很丢包的路径

Queqiao 作者实测过的目标路径（见上游仓库 `docs/PATH-CHARACTER-20260813.md`）：

- **下行丢包率 42%～45%**，而且**和发送速率无关**
- 上行没有对应的丢包底噪，容量也不同
- 往返时延（**RTT**，一个包从 A 到 B 再回到 A 的时间）约 200 毫秒

**RTT（Round-Trip Time，往返时延）** —— 后文所有延迟计算都基于它。一条 200 毫秒 RTT 的路径上，
一次"丢了再重传"的往返就要花掉 200 毫秒。

### 1.2 丢包有两种，后果完全相反

这是整份文档里最重要的一次区分。

想象一条路：

- **拥塞（congestion）**：路上车太多，互相堵住了。**减速有用** —— 车少了就不堵了。
- **擦除（erasure）**：路上随机有个坑，或者运营商随机扔掉一部分车。**减速没用** ——
  无论你开多慢，该被扔的还是被扔。

**怎么区分？** 把发送速率降一半，看丢包率会不会跟着降。

- 降速后丢包率下降 → 是拥塞，退让是对的
- 降速后丢包率不变 → 是擦除，退让只会白白损失带宽

Queqiao 目标路径是**擦除**：42% 的丢包在远低于链路容量时就存在，与速率无关。

> **这个区分决定了整套设计。** 因为擦除不会因为退让而好转，所以不能把丢包当成拥塞信号。
> Queqiao 的做法是：**刹车信号改用延迟**（队列里最多只能积压一个"带宽时延积"），
> 而把测出来的擦除率只用在两件事上 —— **算修复码要发多少**，和**把拥塞窗口补回来**。

**带宽时延积（BDP, Bandwidth Delay Product）** —— 一条链路在"一个 RTT 的时间"里能传多少字节。
链路带宽 × RTT。往这条链路上塞超过一个 BDP 的数据，队列就开始积压，往返时延随之上升。

### 1.3 FEC 是什么，为什么它是 Queqiao 的精髓

**FEC（Forward Error Correction，前向纠错）** —— 发送时除了原始数据，额外发一些**修复符号**
（repair symbol）。每个修复符号是若干原始符号的**异或**（XOR，逐位比较，不同为 1）。
接收端收到足够多的修复符号后，即使丢了原始符号，也能把它算出来。

打个比方：寄 10 张明信片，再多寄 1 张"这 10 张的异或"。如果其中任意 1 张丢了，
用那张异或就能把它算回来。

**为什么这在长 RTT 路径上值钱**：普通重传（ARQ）必须先知道"我丢了什么"，才知道要补什么 ——
这需要等对方的反馈，一来一回就是一个 RTT（这里 200 毫秒）。FEC 不需要等：
修复符号是**提前发出去的**，丢了当场就能补上，没有额外往返。

**异或的世界（GF(2)）** —— 在只含 0 和 1 的算术里，"加法"就是异或，解方程就是高斯消元。
本实验里的 FEC 解码就是在这个世界里做的：把收到的每个符号当成一个方程的一行，
用消元法把"未知数"逐个解出来。

> **注意一个常被误解的点**：FEC 的代价是**额外字节**。在丢包率 p 下，一次性发码
> （不看反馈、盲发修复符号）的理论最小开销约 p/(1−p)。p = 0.4 时约 67%。
> 所以 FEC 买的**不是字节，是延迟**。Queqiao 的设计文档也是这么分的：
> 短交互流量用 FEC，长批量流量退回重传（重传更省字节）。

### 1.4 Queqiao 的三层结构

用后面会反复提到的三个词：

| 层 | 做什么 | 本次实验是否涉及 |
| --- | --- | --- |
| **入口** | 应用把流量交给传输层（Queqiao 用 SOCKS5，本地代理） | 是（实验用 UDP 直发代替） |
| **传输** | 分帧、编号、确认、重传、FEC 修复 | 是（核心） |
| **控制策略** | 判断链路能跑多快、什么时候该退让 | 是（搬进内核的那部分） |

还有一个 Queqiao 特有的概念：

> **共享路径模型（shared path model）** —— Queqiao 认为：多个应用流量虽然最终目的地不同，
> 但在到达网关之前**走的是同一段难走的链路**。所以这段链路的丢包率、带宽、时延应该只测一次、
> 共享给所有流量，而不是每条连接各测各的。

这个概念在本次实验里意外地变得更重要了（见 §7.3）。

# 第二部分 · 内核提供了什么

## 2. 实验环境

| 项目 | 值 |
| --- | --- |
| 内核 | Linux **7.0.14-orbstack**（arm64，BTF 完整，cgroup v2，BPF JIT 开启） |
| 容器运行时 | OrbStack 的 Linux 虚拟机 |
| 规格 | **1 vCPU / 2 GB** —— 只够验正确性，吞吐数字是下限不是上限 |
| 内核源码 | 为了查内核行为，下载了 linux-source-6.8 做参考 |

**BTF（BPF Type Format）** —— 内核把自己所有结构体的字段、类型、偏移写成的一份二进制"类型描述"。
后面讲 CO-RE 时会用到它。

**JIT（Just-In-Time，即时编译）** —— 内核对 BPF 程序做的一次性翻译，把字节码变成机器码。
这是 BPF 能跑得动的原因。

## 3. BPF 是什么

**BPF（Berkeley Packet Filter）** —— 写在 C 里、编译成字节码、由内核加载并即时编译成机器码的小程序。
它可以挂在内核的很多位置：网卡收发包时、socket 收发数据时、TCP 决定拥塞窗口时……

BPF 程序不是"调用内核函数"，而是**被内核在特定时机回调**。这个模型决定了后面所有的能力边界。

理解 BPF 需要三个概念：

### 3.1 BPF map：BPF 程序之间唯一能共享状态的地方

**BPF map** 是内核里的哈希表或数组。BPF 程序可以读它、写它；用户态程序也能读它。
想在一个 BPF 程序里保存"每条连接的状态"，唯一办法就是一张 map。

### 3.2 CO-RE：让同一个二进制在不同内核上跑

**CO-RE（Compile Once – Run Everywhere，一次编译到处运行）** —— BPF 程序里可以写
`sk->sk_pacing_rate` 这样的字段访问。编译时只把**字段名**记下来；程序**装载时**，
由用户态的 libbpf 对着运行中内核的 BTF 算出真实偏移，改写指令里的常数。

这样同一个二进制能在字段位置不同的多个内核版本上直接跑，不需要为每个内核重新编译。

本次实验所有 BPF 程序都用了 CO-RE，而且全部是**部分定义**的结构体 —— 只声明真正用到的字段：

```c
struct sock {
	struct sock_common __sk_common;
	unsigned long sk_pacing_rate;
	unsigned long sk_max_pacing_rate;
	__u32 sk_pacing_status;
} __attribute__((preserve_access_index));
```

内核会按字段名去真实结构体里找偏移，所以本地定义残缺没有关系。

### 3.3 程序类型：能挂在哪儿，决定了能做什么

BPF 有几十种"程序类型"，每种对应内核里的一个挂载点。本次实验用到三种：

| 类型 | 挂载点 | 本次用途 |
| --- | --- | --- |
| `SCHED_CLS`（tc） | 网卡的流量整形层 | 尝试在包路径上加密 FEC |
| `TRACING`（fentry） | 挂在某个内核函数上 | 同上，换个挂载点再试 |
| `STRUCT_OPS` | 内核的"可插拔函数表" | **接管 TCP 拥塞控制** |

## 4. 发现一：内核的拥塞控制可以整个换成 BPF 程序

这是本次调研最实的一个结果。

### 4.1 什么是拥塞控制

TCP 有一套决定"现在能发多快"的规则，叫**拥塞控制算法**（Linux 内置 reno、cubic、BBR 等）。
它决定两个量：

- **拥塞窗口（cwnd）** —— 未被确认的在途字节数上限
- **发送速率（pacing rate）** —— 实际往网卡上发的速率

拥塞控制是内核 TCP 栈的一部分，历史上只能用 C 写、内置进内核。

### 4.2 BPF 怎么接管它

内核把 TCP 拥塞控制做成了一张**函数表**（`struct tcp_congestion_ops`），
每个槽位是一个回调：初始化、算慢启动阈值、算窗口、算速率……
`BPF_PROG_TYPE_STRUCT_OPS` 这种 BPF 程序类型，就是让你用 BPF 填这张表。

内核在 `net/ipv4/bpf_tcp_ca.c` 里为这张表定义了三类约束：

**（a）回调里能拿到什么**

回调的第一个参数是 `struct sock *`，内核的验证器会把它**提升**成 `struct tcp_sock *`
（`tcp_sock` 是 TCP 专用的 socket 结构体，嵌在 `sock` 里）。

**（b）哪些字段允许写** —— 这是一份**白名单**，非常窄：

```
sock.sk_pacing_rate          sock.sk_pacing_status
icsk_ca_priv                 icsk_ack.pending
tcp_sock.snd_cwnd            tcp_sock.snd_cwnd_cnt
tcp_sock.snd_ssthresh        tcp_sock.ecn_flags        tcp_sock.app_limited
```

写白名单以外的字段，内核直接拒绝：

```
no write support to tcp_sock at off 512
```

> 顺便注意：`sk_max_pacing_rate`（单连接发送速率上限）**不在白名单里**，写不了。
> 而 `sk_pacing_rate`（实际发送速率）在，可以写。这两个名字很像，含义完全不同。

这份白名单其实**刚好够一个拥塞控制器用**：调速率、调窗口、调慢启动阈值，
外加 `icsk_ca_priv`（每连接私有存储区）用来放自己的状态。

**（c）哪些回调是必填的**

```
必填：ssthresh、undo_cwnd、以及 cong_avoid / cong_control 二选一
不支持：get_info
```

> `undo_cwnd` 的作用是"退出快速重传时，窗口恢复成多少"。内核会检查它非空，
> 少了就直接拒绝注册 —— 这个约束是踩出来的，最初只填了 `init`/`cong_control` 就注册失败。

**（d）可以调用的内核函数**

BPF 拥塞控制器可以调用一批内核 kfunc（内核函数以 BPF 可调用的形式导出）：
`tcp_reno_undo_cwnd`、`tcp_reno_ssthresh`、`tcp_reno_cong_avoid`、
`slow_start`、`tcp_cong_avoid_ai`、`bpf_tcp_send_ack`、`sk_storage_get/delete`。

### 4.3 实验：把 Queqiao 的控制律搬进内核

Queqiao 的擦除感知控制器（上游 `internal/congestion/erasure.go`）逐条对应：

| Queqiao（Go 代码） | BPF 内核控制器 |
| --- | --- |
| 共享路径模型里的交付速率估计 | 内核给的 `rate_sample.delivered / interval_us` |
| 区分"擦除"与"拥塞" | `rate_sample.losses / (losses + acked_sacked)` |
| **延迟刹车**：往返时延不超过最小值的两倍 | `factor = min_rtt / (smoothed_rtt − min_rtt)`，连续缩放 |
| **补偿对赌**：多发必须换来多收，否则退回 | `comp_ppm` 只在交付真的涨了才继续加，否则打九折 |
| 设置发送速率 | `sk->sk_pacing_rate`（白名单内） |
| 设置拥塞窗口 | `tp->snd_cwnd`、`tp->snd_cwnd_cnt`（白名单内） |

**实测输出**（从 map 里读出来的控制器内部状态）：

```
sock=ffff00000d22af80 bw=255207 B/s min_rtt=5126us smooth=91360us comp=1000000ppm calls=412
```

- `calls=412` —— **内核调用了这个控制器 412 次**
- `bw=255207 B/s` —— 交付速率估计在实时更新
- `min_rtt=5126us` / `smooth=91360us` —— 往返时延的最小值和平滑值
- `comp=1000000ppm` —— 补偿系数（百万分之一为单位），环回无丢包时正好是 1.0，符合预期

注册后，内核的可用拥塞控制列表变成：

```
$ cat /proc/sys/net/ipv4/tcp_available_congestion_control
reno cubic qk_erasure
```

任何 socket 用 `setsockopt(TCP_CONGESTION, "qk_erasure")` 就能选中它。

**结论：Queqiao 最核心的控制策略可以完全运行在内核里，没有任何用户态进程参与控制回路。**

### 4.4 但这条路走不到加密

同一个内核里确实有**内核态的 AEAD（带认证的加密）**：BPF 程序可以创建加密上下文、
用 `gcm(aes)` 这类算法加密解密。这些函数在运行中内核的 BTF 里都能查到。

但它们**从普通程序类型调不到**。实测，从 tc 程序和 fentry 程序装载时都被内核拒绝：

```
calling kernel function bpf_crypto_ctx_create is not allowed
```

它被内核绑定在一个特定的挂载目标上，普通包路径程序无权调用。

> **后果**：想在内核里做一个加密隧道，加密那一层得靠内核自带的东西
> （IPsec 的 ESP、WireGuard、tls_sw），不能指望 eBPF 自己做密码学。

# 第三部分 · 实验

## 5. 实验台

### 5.1 拓扑

```
qk-cl (客户端, NAT 后面)                      qk-gw (网关)
  fd00:db8:9::20   源地址 1        ──UDP──▶   fd00:db8:9::10
  fd00:db8:9::21   源地址 2        ──UDP──▶   fd00:db8:9::11
  fd00:db8:9::22   源地址 3        ──UDP──▶   fd00:db8:9::12
```

两个特权容器接在同一个 docker 网络上，开了 IPv6。客户端在 NAT 后面 —— 这正是 **CGNAT** 的形状：
只能客户端主动发起，网关不能反向连接。

### 5.2 怎么精确注入丢包

用内核自带的两个工具：

- **netem** —— 网络模拟器，能给网卡加延迟、抖动、丢包、限速
- **qdisc（队列规则）+ flower 过滤器** —— 流量整形层和按报文字段分类的匹配器

组合起来就能做到"**按源 IP 分别注入不同的丢包率**"：

```sh
tc qdisc add dev eth0 root handle 1: prio bands 4
tc qdisc add dev eth0 parent 1:2 handle 12: netem limit 10000 delay 100ms loss 40%
tc qdisc add dev eth0 parent 1:3 handle 13: netem limit 10000 delay 100ms loss 40%
tc filter add dev eth0 protocol ipv6 parent 1: prio 2 flower src_ip fd00:db8:9::20/128 flowid 1:2
```

关键点：**每个源地址挂一个独立的 netem 实例**，所以三条通道的丢包过程互相独立。
这正是"运营商按 IP 算丢包"的模型。

## 6. 实验一：三个源地址是不是三条独立信道

### 6.1 测量方法：开环探针

**开环（open loop）** 指发送速率由自己决定，不等对方的反馈。这点很重要：
如果让 TCP 来测，TCP 自己会因丢包降速，测出来的"速率"反映的是 TCP 的反应而不是链路。

探针发带序号的数据包，接收端数收到的个数和序号空洞，就能算出丢包率和交付速率。

### 6.2 结果

| 配置 | 交付 | 总丢包 |
| --- | ---: | ---: |
| 干净链路（无丢包） | 240 Mbit/s | 0% |
| 1 个源地址，40% 丢包 | 11.45 Mbit/s | 40.3% |
| **3 个源地址，每个独立 40% 丢包** | **32.62 Mbit/s** | 43.4% |

**2.85 倍。** 每通道的丢包率没有变化（40% 左右），但总交付涨了近三倍。

### 6.3 这个结果和 Queqiao 自己的结论不矛盾

Queqiao 的设计文档（`docs/DESIGN.md`）否掉过多路径聚合，理由是：

> 把同样的负载拆到 1、2、4、8 条四元组上，总交付不变 —— 没有每连接限速器，
> 也没有独立容量可以聚合。

**注意那是同一个 IP 的不同端口。** 本实验用的是**三个不同的源 IP**，
是运营商"按 IP 算"时才成立的场景。两者是不同的命题，Queqiao 没有测过后者。

### 6.4 一个必须分开测的东西

"丢包独立"和"容量独立"是两回事：

- 运营商按 IP 丢包 ⇒ 多个地址 = 多条独立**擦除**信道 ⇒ FEC 可以跨通道修复
- 但如果带宽是共享瓶颈（一个 policer 限速所有 IP）⇒ 多地址**不增加总带宽**

所以在真实路径上要测**两个数**：每个源 IP 的丢包率，以及**三条通道同时开时的聚合交付**。
后者是 3 倍还是 1 倍，直接决定架构。

## 7. 实验二：FEC 传输原型

### 7.1 原型设计

写了一个跨多通道的 FEC 传输（`qkfec.c`），两种模式：

**FEC 模式**

- 数据切成固定大小的符号（1184 字节）
- 每 32 个符号一组，发送时先发全部源符号，再发 **R 个修复符号**
- 每个修复符号 = 组内**随机子集**的异或，并附带一个 32 位掩码说明它覆盖了哪些符号
- 接收端对每组维护一个**异或方程组**，用消元法解；解出来的符号立刻上交

**DUP 模式**（最简单的对照）

- 每个符号发**两份**，放在两个不同的通道上
- 接收端取先到的那份
- **完全不需要编码数学**

两种模式里，符号轮流分配到不同通道（修复符号用不同的相位错开），所以通道之间是真的在分担。

### 7.2 FEC 模式在丢包下的表现

修复符号数量直接决定能救回多少：

| 每组修复符号数 | 开销 | 解出的组 | 比例 |
| ---: | ---: | ---: | ---: |
| R = 24 | 75% | 104 / 221 | 47% |
| **R = 40** | **125%** | **212～221 / 221** | **96～100%** |

R = 40 时 221 组基本全解出。这也验证了 §1.3 说的"一次性发码的开销下界约 p/(1−p) ≈ 67%"：
随机掩码的修复符号里有相当一部分退化成平凡方程，所以实际要 125% 才够。

### 7.3 关键观察：DUP 几乎和 FEC 一样好

| 模式 | 交付 | 符号完好率 | 残余丢包 |
| --- | ---: | ---: | ---: |
| FEC（R = 40） | 97.4 Mbit/s | 96% | — |
| **DUP（2 份拷贝）** | **96.2 Mbit/s** | **约 84%** | **约 16%** |

DUP 的残余丢包正好等于 **p² = 16%** —— 两份拷贝分别在两条独立通道上，
两份都丢的概率就是 p²。**理论完全对得上。**

> **这个观察对内核化非常重要**：DUP 不需要任何编码数学，只需要"把一个包复制一份、
> 改掉源地址、发到另一条通道"。这在 eBPF 里有现成原语
> （`bpf_clone_redirect` 克隆报文 + 改写 IPv6 源地址）。

### 7.4 相关突发丢包下 FEC 依然成立

用 netem 的 **gemodel**（Gilbert-Elliott 模型）制造**相关丢包**：
所有地址被**同一个**状态机打断，突发期一起丢。实测平均丢包率约 **15%**
（比前一个实验的 40% 低，所以这里的对比是对 FEC 更不利的）。

| 传输 | 丢包 | 交付 |
| --- | ---: | ---: |
| TCP | ~15% 突发 | 0.263 Mbit/s |
| **FEC，3 个 IP** | ~15% 突发 | **101.5 Mbit/s**（221/221 组全解出） |

FEC 不怕突发：一次突发很难同时抹掉一整组符号**加上**它的全部修复符号。
注意这里 TCP 的丢包率比前一个实验低一半，交付却只涨了 4 倍 —— 突发丢包对 TCP 的伤害更大，
因为 TCP 把突发当成拥塞而猛烈退让。

### 7.5 TCP 基线

同一条路径（40% 丢包，200 毫秒 RTT）上的 TCP：

| 传输 | 交付 payload | 相对 TCP |
| --- | ---: | ---: |
| TCP（cubic），单流 | **0.063 Mbit/s** | 1× |
| FEC，1 个 IP | 32.4 Mbit/s | **514×** |
| FEC，3 个 IP | 97.4 Mbit/s | **1546×** |
| DUP，3 个 IP | 96.2 Mbit/s | 1527× |
| TCP（~15% 突发丢包） | 0.263 Mbit/s | 1× |
| FEC，3 个 IP（~15% 突发丢包） | 101.5 Mbit/s | **386×** |

> **这是整份文档里最有说服力的一组数**：在 40% 丢包的路径上，
> TCP 只剩 63 Kbit/s，而 FEC 能跑满 97 Mbit/s。差 500 倍以上。
>
> 顺带说明：TCP 差成这样不是实现问题，是数学问题。
> 经典的 Mathis 公式给出的稳态吞吐约为 `MSS / (RTT × √p)`，
> 代入 1448 字节、0.2 秒、p = 0.4，约为 92 Kbit/s —— 和实测同量级。

# 第四部分 · 结论与设计

## 8. 四个结论

**结论一：Queqiao 的控制策略可以完整搬进内核。**
BPF 拥塞控制接口的白名单刚好覆盖一个拥塞控制器需要的全部能力
（速率、窗口、慢启动阈值、每连接私有区）。实测内核在实时调用它。

**结论二：纯 eBPF 做不到加密。**
内核的 AEAD 接口对普通程序类型关闭。加密层必须用内核自带的东西（IPsec / WireGuard / tls_sw）。

**结论三：per-IP 丢包这个前提成立，多地址就是多条独立信道。**
实测 2.85 倍（三个地址）。这给出了一条 Queqiao 自己没走过的路。

**结论四：但传输层必须在 IP 之上，TCP 帮不上忙。**
TCP 的连接由**四元组**（源 IP、源端口、目的 IP、目的端口）唯一确定，
接收端没法分别向不同的源 IP 发确认，所以**跨地址的容量聚合用现成 TCP 做不到**。

> IP 层的重复拷贝倒是能和普通 TCP 配合（内核会丢弃重复的报文段），
> 但它只能把丢包从 p 降到 p² = 16%，而 TCP 在 16% 丢包下依然不可用。
> **冗余本身救不了 TCP，必须有真正的多路径传输层。**

这也解释了为什么"直接用 WireGuard"不是答案：WireGuard 自己会重传（是可靠传输），
叠 FEC 没意义；而且它不分片，拿不到多地址聚合。

## 9. 三条实现路线

| 路线 | 内容 | 代价 | 拿到什么 |
| --- | --- | --- | --- |
| **A** | MPTCP 多源地址子流 + 每子流挂 §4 的 BPF 拥塞控制器 | 中 | 全内核、无用户态、跨地址容量聚合。**没有 FEC**（MPTCP 不做 FEC）。注：本机内核没编 MPTCP，主线内核有 |
| **B** | TUN 设备 + 一个很小的用户态传输进程（§7 那套） | 小 | 实测 97 Mbit/s。仍有用户态进程，但只是读写 TUN 和 socket，不需要特权、不需要常驻服务 |
| **C** | 全 BPF 数据面：tc 层自己构造外层 UDP 报文、计算修复符号、接收端重组后注入内核协议栈 | 大（约 1500 行 BPF） | 全内核 + 真 FEC。加密仍要靠 IPsec |

**建议：B 先落地，A 并行验证，C 作为目标。**

理由：B 已经把"值不值得做"证明清楚了（500～1500 倍）；A 能直接复用 §4 已经写好的
BPF 拥塞控制器；C 的两块最难的部分（构造报文、注入内核栈）都有可用的内核原语，
但工作量最大。

## 10. 下一步

**（a）先在真实路径上测 per-IP 独立性** —— 这是整个架构的前提，探针是现成的：

```sh
# 在客户端上，对每个源地址各跑一次
./probe send <源IP> <网关IP> <端口> <pps> <字节> <秒数>
```

要拿到三个数：每个源 IP 的实际丢包率、每条通道的交付速率、**三条通道同时开时的聚合交付**。
聚合是 3 倍还是 1 倍，直接决定路线 A/C 值不值得投。

**（b）量 FEC 的延迟优势** —— 本次只量了吞吐。FEC 真正买到的是"零往返"，
需要量首字节延迟和丢包停顿，与 ARQ（重传）对照。这是 FEC 与重传的分水岭。

**（c）确认目标内核的 MPTCP 与加密能力** —— MPTCP 是否编译进来、IPsec 能不能配。

## 附录 C：踩过的坑

**坑 1：BPF 程序不写 `__builtin_preserve_access_index`，字段访问会被内核拒绝。**
BPF 拥塞控制器的回调参数默认被当成"上下文指针"，只能读不能按字段访问。
必须用 `BPF_PROG` 宏（它会自动加上这个标记），否则报
`invalid bpf_context access off=512 size=8`。

**坑 2：kfunc 的类型必须和内核的"种类"一致，名字无所谓。**
libbpf 校验一个 kfunc 声明时，只比较 BTF 的**种类**（指针、结构体、整型……），
**不比较名字，也不比较结构体的字段**。但内核前向声明过的类型，本地也必须写成完整结构体；
内核声明成 `const` 的，本地也要 `const`。否则报
`func_proto [30] incompatible with vmlinux [38765]`。

**坑 3：`struct hdr` 是 20 字节，`HDRSZ` 写成了 16。**
结果 `kind` 字段根本没被复制过去。FEC 模式因为只用掩码、不看 `kind`，**碰巧还是对的**，
而依赖 `kind` 的 DUP 模式完全失效 —— 表现为"收到 8000 多个报文但一个符号都没解出来"。
教训：结构体大小和线上常量之间要加编译期断言
（`_Static_assert(sizeof(struct hdr) == HDRSZ, ...)`）。

**坑 4：kernel 6.8 的 uapi 头文件太老，没有 `bpf_test_run_attr`。**
容器里的 linux-headers 是 6.8，`union bpf_attr` 里的 `BPF_PROG_TEST_RUN` 段还是老布局。
最后绕开 libbpf，直接用原始系统调用。

**坑 5：实验脚本里收发窗口没对齐，"丢包"其实是窗口错位。**
接收端窗口比发送端短 1 秒，尾部的数据包根本没被发出去，
一开始被误读成丢包。修正后丢包率才和 netem 配置对得上。
