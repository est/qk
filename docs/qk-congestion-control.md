# qk —— 把 Queqiao 的控制律搬进内核

**一个用 eBPF 实现的 TCP 拥塞控制，以及它到底能做到什么**

---

## 这份文档是什么

上一份文档 [`kernel-native-transport.md`](kernel-native-transport.md) 回答了"内核能不能做这件事"。
这份文档回答下一个问题：**能不能只换掉控制策略，别的都不动？**

结论是：**能，在丢包路径上效果显著；但它有一个天花板，而且这个天花板不在控制律里，
在内核自己的重传机制里。**

- 实现：`src/cc/`（代码说明见该目录的 README）
- 测量：`src/bench/`（一个按 socket 选拥塞控制的吞吐基准 + 可控丢包的实验台）
- 本文所有数字都是实测，实验台可复现（见文末）

## 一、要复现的东西是什么

Queqiao 的控制律在内核里的对应物是一个拥塞控制算法。内核的 TCP 栈有一套"现在能发多快"的规则
（Linux 自带 reno、cubic、BBR），历史上只能用 C 写死进内核。

但内核把这套规则做成了一张**函数表**（`struct tcp_congestion_ops`），每个槽位是一个回调。
`BPF_PROG_TYPE_STRUCT_OPS` 这种 BPF 程序类型，就是让你用 BPF 填这张表。

所以问题变成：**Queqiao 的控制律能不能填进这张表？**

### 控制律本身

Queqiao 的核心主张是：这条路径是**擦除**信道，不是拥塞信道。丢包率和发送速率无关，
所以"丢包就退让"会把带宽白白丢掉。

因此它的控制律有三条与常规拥塞控制不同：

1. **刹车信号是延迟，不是丢包。** 平滑后的往返时延不得超过路径最小往返时延的某个倍数；
   超过之后按比例连续缩小发送速率。
2. **丢包不缩窗口。** 在这条路径上丢包不是拥塞，缩窗口只会让交付速率跟着掉，然后下一次丢包再缩一次。
3. **测出来的擦除率只用于两件事**：把窗口算大（好让"能到达的字节"填满一整个往返），
   以及把配速速率算对。

另外，补偿被当成一次**下注**：调高它是在声称"多发就能多收"，这个声称要用实测的交付速率来检验。

> 后面会看到：这一条**实现不了**，因为内核给控制器的速率样本在不同内核版本上单位不一致
> （有的版本里 `delivered` 数的是段数而不是字节）。控制器最终不依赖速率估计。

## 二、内核给了一张多窄的纸

这是动手之前必须知道的。内核在 `net/ipv4/bpf_tcp_ca.c` 里对拥塞控制器做了三类限制。

### （a）能写哪些字段

一份显式白名单，只有这些：

```
sock.sk_pacing_rate          sock.sk_pacing_status
icsk_ca_priv                 icsk_ack.pending
tcp_sock.snd_cwnd            tcp_sock.snd_cwnd_cnt
tcp_sock.snd_ssthresh        tcp_sock.ecn_flags        tcp_sock.app_limited
```

写白名单以外的字段，内核直接拒绝：

```
no write support to tcp_sock at off 512
```

这张表**刚好够一个拥塞控制器用**：调速率、调窗口、调慢启动阈值，外加 `icsk_ca_priv`
（每连接私有存储区）放自己的状态。

> 注意 `sk_max_pacing_rate`（发送速率上限）和 `sk_pacing_rate`（实际发送速率）只差一个前缀，
> 前者**不在**白名单里，后者**在**。

### （b）哪些回调必填

```
必填：ssthresh、undo_cwnd、以及 cong_avoid / cong_control 二选一
不支持：get_info
```

`undo_cwnd` 是最容易漏的一个：内核会检查它非空，缺了直接拒绝注册。
它要返回"退出快速重传时窗口恢复成多少"。

### （c）拿到内核的什么所有权

**一个拥塞控制如果提供了 `cong_control` 回调，内核就把配速速率的所有权交给它**
（内核自己不再调用 `tcp_update_pacing_rate()`）。这正是 BBR 那类控制器的工作方式，
也决定了正确的结构是：**速率是控制量，窗口是速率的结果。**

### （d）回调长什么样，有两个坑

**坑一：`cong_control` 的第三个参数不是往返时延。** 内核的回调签名是：

```c
void (*cong_control)(struct sock *sk, u32 ack, int flag, const struct rate_sample *rs);
```

第三个参数是 **ACK 的标志字**。往返时延在 `rs->rtt_us` 里。
一开始把 `flag` 当成时延用，于是"最小往返时延"被一个 16.7 毫秒的标志值钉死，
延迟上界变成 33 毫秒，而真实往返是 100 毫秒 —— **刹车一直误触发，配速永远压在地板上**。

**坑二：`cong_control` 是每个被确认的报文段都调用一次**，而速率估计和容量探测
是"往返"量纲的。按 ACK 推进会让探测窗口在一个 RTT 内涨几十倍，直接把路径打爆。
必须自己按往返计时。

**坑三（更隐蔽）：`__attribute__((unused))` 不能写在 `BPF_PROG` 的参数列表里**，
因为那个宏靠数参数个数来选择从上下文数组取参的变体，属性会被当成参数。
症状是装载时内核报 `jump out of range`。

## 三、qk 的设计

最终版本**不依赖交付速率估计**。三个量就够：

| 状态 | 含义 |
| --- | --- |
| `min_rtt_us` / `smoothed_rtt_us` | 路径的最小往返时延和平滑值 |
| `floor_ppm` | 擦除底噪：最近若干轮里最低的丢包率 |
| `probe_cwnd` | 当前认为路径能承载的窗口 |

每轮（一个往返）做三件事：

1. **更新往返时延。** 最小值作为底噪，但底噪会缓慢（1/16 每轮）向平滑值回升 ——
   最小值太脆弱，一个异常小的采样就能把它钉死，然后延迟上界永远低于真实往返时延，
   刹车就一直误触发。

2. **更新擦除底噪。** 本轮丢包率与历史最低值取小；底噪以每轮 75% 的速度慢慢回升，
   这样路径真的变差之后最终能被补偿到。

3. **按延迟上界调节窗口。** 平滑往返时延在上界以内 → 窗口每轮涨 1/8；超过上界 → 每轮退 1/8。
   上界 = 最小往返时延 × `brake_ratio_pct`（默认 200%，即两倍）。

然后：

```
窗口 = 探测窗口 × 补偿          补偿 = 1 / (1 − 擦除底噪)
配速速率 = 窗口 × 段长 / 最小往返时延
```

窗口必须比"带宽时延积"大，因为只有 `1−p` 的在途字节能到达。

**丢包不缩窗口**：`ssthresh` 返回的是当前窗口（和探测窗口的较大者），
所以内核在丢包时不会把窗口砍到 2。内核在 `cong_control` 模式下本来也不会在恢复结束时
重置窗口（`tcp_end_cwnd_reduction()` 里有 `if (ca->cong_control) return;`），
但快速重传期间的**比例窗口削减**和**重传超时后的窗口重置**仍然会发生，控制器管不了。

## 四、测量

### 实验台

两个特权容器接在同一 docker 网络上，开 IPv6。客户端在 NAT 后面（这正是 CGNAT 的形状）。
丢包用内核的 `netem` 注入，**按源 IPv6 地址分流**，每个地址挂一个独立的 netem 实例
—— 这就是"运营商按 IP 算丢包"的模型。

路径：100 ms 往返时延（单向 100 ms 延迟），40% 丢包。

### 结果

| 拥塞控制 | 交付吞吐 | 相对 cubic |
| --- | ---: | ---: |
| cubic | **0.14 Mbit/s** | 1× |
| **qk** | **0.89 Mbit/s** | **6.4×** |

五次重复：cubic 0.14 ± 0.02，qk 0.89 ± 0.52（最好的一次 1.51，是 cubic 的 11 倍）。

> **这一节的结论后来被推翻了，保留原文是因为它记录了当时的方法。**
> 对照组选得太弱了：真实内核里还装着 **BBR**，而 BBR 在同一条路径上比 cubic 高两个数量级。
> 拿 qk 和 cubic 比，比的其实是一个不该赢的基线。第五节给出修正后的结论。

**方差很大**，这是如实报告：窗口在"探测上限"和"内核重传把它砸回 1"之间来回摆。

### 干净路径上会略慢

| 拥塞控制 | 交付吞吐 |
| --- | ---: |
| reno | 23.64 Mbit/s |
| cubic | 23.71 Mbit/s |
| **qk** | **22.06 Mbit/s** |

**慢 7%。** 原因：在这条路径上延迟上界从来没被碰到（往返时延一直是 25 毫秒），
所以窗口一路涨到上限，配速速率跟着涨到路径容量的二十倍，发送变成突发式。
在这台**单核**虚拟机上，突发式发送的效率明显低于 cubic 的平滑配速。

这是这条路径的性质，不是所有干净路径的性质 —— 但在没有别的证据之前，如实记为 **7% 的回退**。

用运行时调参可以把折中调向另一头（`qkctl tune --set max_cwnd=200 --set brake_ratio_pct=125`），
干净路径掉到 5.5 Mbit/s（窗口太小），丢包路径仍有 5 倍。**默认值是这两者之间较好的折中。**

### 和上一份文档里的 FEC 传输比

同一条路径上，FEC 传输做到了 **97 Mbit/s**。

```
cubic    0.14 Mbit/s  ▏
qk       0.89 Mbit/s  ▏▏▏▏▏▏
FEC     97.00 Mbit/s  ▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏
```

**差了 109 倍。** 这个差距不是控制律不好，是**天花板不在控制律里**。

## 四·五、在真实 VPS 上实测

实验台搬到了一台真实的 VPS 上（Ubuntu 22.04，**Linux 5.15**，x86_64，1 核），
路径是"本地 → VPS"：往返时延 **238 毫秒**，ICMP 无丢包。
VPS 端跑一个只管发字节的 listener，**按 socket 选拥塞控制**（`setsockopt(TCP_CONGESTION)`），
本地用 curl 下载测速。

| 拥塞控制 | 干净路径（丢包 ~2%） | 注入 40% 丢包 |
| --- | ---: | ---: |
| cubic | 0.37 Mbit/s | 0.03 Mbit/s |
| **bbr** | **49.0 Mbit/s** | 0.07 Mbit/s |
| **qk** | **0.49 Mbit/s** | 0.06 Mbit/s |

三件事从这里冒出来。

### （1）内核的拥塞控制接口在版本之间变过形状

这台 5.15 内核的回调是：

```c
void (*cong_control)(struct sock *sk, const struct rate_sample *rs);   /* 两个参数 */
```

而 7.x 上是：

```c
void (*cong_control)(struct sock *sk, u32 ack, int flag, const struct rate_sample *rs);
```

**两个版本传的都是 `struct rate_sample`**，只是新版本多带了确认字节数和标志字。

而我最初给"两参数"变体写的是 `struct ack_sample` —— 另一个结构体。
结果控制器把 `rate_sample.prior_delivered` 当成了往返时延：
实测路径的往返是 238 毫秒，控制器却以为底噪是 **1.9 毫秒**，
于是延迟上界变成 3.8 毫秒，**刹车永远处于触发状态**，窗口永远长不大。

这就是为什么这个控制器一开始在真实路径上只有 0.49 Mbit/s。
现在 `qk_abi` 会从运行中内核的 BTF 里读出这个成员的原型、报告参数个数，构建时自动选对应的变体。

### （2）这台内核不允许写配速速率，而那恰好是长 RTT 路径的关键

5.15 的可写字段白名单里没有 `sk_pacing_rate`，程序一写就被拒：

```
no write support to tcp_sock at off 464
```

而 `cong_control` 模式的意义正是"内核把配速速率的所有权交给控制器"。
拿不到它，就只剩窗口这一个控制量 —— **而只有窗口的控制量在 238 毫秒的路径上必然振荡**：
窗口涨到把瓶颈队列灌满 → 平滑往返时延冲到 1.78 秒 → 延迟上界触发 → 窗口塌缩 → 吞吐塌到 cubic 的水平。

实测把延迟上界从 2 倍放宽到 8 倍，吞吐只从 0.49 涨到 0.73 Mbit/s —— 刹车是限制之一，但不是主要矛盾。

### （3）BBR 为什么赢

BBR 赢在**控制速率、同时把窗口保持得大**。它在拥塞控制模式下不会被内核的窗口削减拖垮，
也不会因为一次丢包就把窗口砍掉。

qk 目前是窗口式的，所以在长 RTT 路径上打不过 BBR。**这不是把参数调一调能解决的，是结构问题。**

### 结论修正

| | 干净长 RTT 路径 | 高丢包路径 |
| --- | --- | --- |
| 任何 TCP 拥塞控制 | cubic 0.37 / bbr 49 / **qk 0.49 Mbit/s** | 全部 0.03～0.07 Mbit/s |
| FEC 传输（实验台实测） | — | **97 Mbit/s** |

两件事因此清楚了：

1. **在长 RTT 路径上，要和 BBR 竞争就得改成速率式的控制**（测交付速率 → 定配速 →
   窗口按 2×BDP 保持宽松）。这条路要求内核允许写 `sk_pacing_rate`，6.x/7.x 允许，5.15 不允许。
2. **在重丢包路径上，任何 TCP 拥塞控制都不管用** —— 包括 BBR。40% 丢包下三个算法都掉到
   0.03～0.07 Mbit/s，而 FEC 传输在同一路径上是 97 Mbit/s。**这正是 FEC 存在的理由。**

所以内核原生的拥塞控制不是终点，它是"没有 FEC 时的兜底"，
而**跨 IP 的 FEC 传输才是主线**。

## 五、天花板在哪

拥塞控制能碰的只有窗口和配速速率。而内核自己的**重传机制**碰不到：

- 快速重传期间的**比例窗口削减**（PRR）由内核执行，控制器无权否决；
- **重传超时**会把窗口重置成"在途报文数 + 1"，然后重新慢启动。

在 40% 丢包的路径上，TCP 的有效丢包率是 `1 − 0.6² = 64%`（重传本身也会被丢）。
每秒钟发生好几次超时，每一次都把窗口砸回 1 个报文段。

**控制器能做的只是把窗口重新撑回去**（它每个 ACK 都会这么做），但撑回去的那段时间里，
在途的字节很少，交付速率就上不去。这解释了为什么 qk 有 6 倍的提升，却离 FEC 的 109 倍还差得远。

> **一句话**：FEC 消除的是"重传"，拥塞控制消除不了。
> 这两条路线是互补的，不是替代关系。

## 六、调过的几轮，和它们的教训

控制器第一版是错的，走了六轮才对。每一轮的教训都值得记下来：

| 版本 | 问题 | 修正 |
| --- | --- | --- |
| v1 | `ssthresh` 按交付速率算丢包后的窗口 → 丢包时把窗口砍到 2，吞吐塌到 0.06 Mbit/s | 丢包不缩窗口（`ssthresh` 返回当前窗口） |
| v2 | 探测窗口每个 ACK 涨 50% → 一个 RTT 内打满上限 → 巨量丢包 → 塌缩 | 探测按**往返**推进，不是按 ACK |
| v3 | 同时控制配速和窗口，两者互相放大 | 只控制一个量：速率是控制量，窗口是结果 |
| v4 | 速率估计没有上限，一个异常采样把估计放大到 877 MB/s，污染了窗口 | 丢弃物理上不可能的采样 |
| v5 | **把 ACK 标志字当成了往返时延** → 延迟上界永远低于真实往返 → 刹车一直误触发 | 时延从 `rs->rtt_us` 取 |
| v6 | 依赖内核的速率样本，而它的 `delivered` 在这个内核上数的是**段数**不是字节 → 速率估计恒为 0 | **彻底去掉速率估计**：窗口改由延迟上界驱动 |

第六轮是决定性的一轮：**当控制律不再需要速率估计之后，它反而更简单也更稳了。**
速率估计需要处理 `is_app_limited`、样本单位、内核版本差异，而延迟上界只需要两样东西：
最小往返时延和当前往返时延 —— 这两个在任何内核上都是同一个意思。

## 七、运维上的几个事实（都踩过）

**拥塞控制的注册是内核全局的，不是 per network namespace。**
在任何一个容器里注册了 "qk"，所有 namespace 的 socket 都能选它。

**注册是"粘"的，已经注册的名字换不掉。** 内核在 `bpf_struct_ops_map_delete_elem()`
里才做注销，而 map 元素只在**删除**时才删 —— 释放 link 并不注销。所以：

- 同一个名字只能注册一次，换内核版本要换名字或重启；
- `qkctl` 因此提供 `--daemon`（持有注册）和 `qkctl unload`（让持有者删除 map 元素，
  从而让内核注销）。

**内核的拥塞控制列表在 `/proc/sys/net/ipv4/tcp_available_congestion_control`，
是全局的，所以 `setsockopt(TCP_CONGESTION, "qk")` 在任何 namespace 都可用。**

**`qkctl load` 默认注册完就返回**（内核自己会保留注册），`--daemon` 才保持进程。

## 八、怎么复现

```sh
# 构建
make -C src/cc container          # 需要 clang + libbpf-dev，在容器里
make -C src/bench build

# 起实验台
cd src/bench
./lab.sh up
./lab.sh loss --rate 40 --delay 100 --mode per-ip

# 把控制器装进客户端容器（注册是全局的，客户端容器里也能选到）
./lab.sh loadcc --object ../cc/build/qk.o

# 对比
./lab.sh compare --cc cubic,qk --duration 15 --repeat 5
```

干净路径对照：

```sh
./lab.sh loss --rate 0 --delay 20 --mode shared
./lab.sh compare --cc reno,cubic,qk --duration 8 --repeat 2
```

> **注意**：内核的拥塞控制注册是全局且不可替换的，所以同一个名字只能注册一次。
> 在一台已经注册过 "qk" 的机器上测新版本，要么用 `make NAME=qk2` 换一个名字，
> 要么先 `qkctl unload` 把旧的卸掉。

## 九、接下来

1. **和 FEC 传输合流。** 上一份文档的结论是：跨 IP 的容量聚合需要 IP 之上的传输层。
   qk 可以作为那个传输层之下的**兜底**：FEC 处理不了的部分（重传、FEC 自身修不回来的残余丢包）
   交给内核的 TCP，qk 负责不让 TCP 在擦除路径上把窗口砍光。

2. **在真实路径上测。** 本文的数字全部来自 netem 模拟的路径。真实运营商路径的丢包是否与速率无关、
   是否成簇、往返时延的抖动形态如何，都会改变控制律的表现。

3. **窗口削减那一环。** 目前只能靠控制器每个 ACK 把窗口撑回去。如果内核能暴露 PRR 的削减点，
   或者允许拥塞控制声明"这条路径的丢包不是拥塞"，收益会大得多 —— 这值得给内核提一个 patch。
